IronLog

An offline-first fitness and health tracking PWA — workouts, nutrition, body metrics, progress photos, AI coach — serving a gym community of about 1,000 users. Designed, built and run solo.

Visit IronLog ↗ Back to projects

What it is

A gym-floor app has to work with no signal, on a phone, mid-set. Everything else follows from that.

The app
  • Workouts — logging, programs, exercise history.
  • Nutrition and body metrics — intake, targets, measurements.
  • Progress photos — stored in object storage and served through signed URLs.
  • AI coach — runs on the user’s own model API key, which stays on their device.
  • Community — friends, feed, groups, direct messages and weekly leagues.
Built for the gym floor
  • Installable PWA with a service worker and an offline page.
  • Every change is saved on the device first; the network is never in the way of logging a set.
  • Sync happens in the background and catches up after a dead zone.
  • Push notifications through Web Push.

How single sign-on works
  • Signing in to any app creates a session on the shared API.
  • The session token is kept in a cookie scoped to ironlog.space, so every subdomain can read it.
  • On first open, each app checks for that cookie, validates it with the API, and pulls the account’s data. No second sign-up.
  • Signing out clears the cookie for all five.
Why separate apps
  • Each app does one job and installs with its own icon, offline scope and service worker.
  • A change to one cannot break the others; they deploy independently.
  • People install only the ones they use.
  • One account and one backend keep identity from drifting between them.

System design

Static front-ends, one small API, one database. The API is the only thing that talks to the database.

Built for reliability and privacy

Four claims from my resume, each with what the code does.

Row-level security on every user table
Database
  • The database key that ships in a web bundle is public by design, so row-level security is the real boundary in front of the data.
  • The API is the only path to the data: it reaches Postgres with a service role, and policies are written so the public key on its own gets nothing.
  • Coach features use a separate, narrower database role: a coach sees a client’s rows only while that client’s consent record says so, and revoking consent takes effect on the next query.
  • Policies are kept as numbered migrations in the API repository.
Hashed PINs with lockout
Sign-in
  • Account PINs are hashed with bcrypt on the server. The plain PIN is never stored.
  • Five wrong attempts lock the PIN for 15 minutes.
  • The API never returns the hash. Clients and the admin dashboard see only whether a PIN is set and whether it is locked.
An offline sync queue that replays on reconnect
Offline
  • When a sync fails, the pending change set goes into an IndexedDB queue on the device.
  • Each queued item records which account it belongs to, so a replay after switching accounts cannot write one person’s history into another’s.
  • Only the newest snapshot is kept, so an older one can never overwrite newer data.
  • The queue replays when the connection returns, using Background Sync where the browser supports it.
An admin dashboard that strips personal data
Admin
  • Admin responses are assembled field by field on the server before they leave the API.
  • Phone numbers come back masked.
  • The PIN hash and lockout timestamp are reduced to two yes/no flags.
  • Admin endpoints require a valid session and an admin account.

Stack

Chosen to run a real product on free and near-free tiers, operated by one person.

Front-end
  • React 18 and Vite 6, one PWA per app.
  • Recharts for trends and analytics.
  • Service worker, web manifest, offline page, Web Push.
  • Static hosting, deployed from the main branch by GitHub Actions.
Back-end
  • Serverless functions for auth, sync, photos, push, social and admin.
  • Supabase Postgres with row-level security; Realtime for live updates.
  • Cloudflare R2 for photos and video.
  • Transactional email for verification and PIN reset.

How to verify, and what is not claimed

Try it; then read the caveats.

Try it
  • Open ironlog.space ↗ and install it from the browser’s install prompt.
  • Turn on airplane mode and log a workout. It saves.
  • Reconnect and watch it sync.
  • Open nutrition.ironlog.space ↗ in the same browser: you are already signed in.
Not claimed
  • “About 1,000 users” is my own figure, not an audited one, and it says nothing about daily use.
  • IronLog and the API are private repositories, so the code behind this page is not public. The four sibling apps are public on GitHub ↗.
  • Not every app syncs everything: some keep data on the device by default.
  • This is a consumer product, not a regulated system. The patterns carry over; the compliance burden does not.
