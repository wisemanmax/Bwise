The Builder

Describe an app in chat. A multi-stage pipeline plans it, builds it, checks it, has a second model review it, fixes what was found, and deploys it once you approve.

View the source ↗ Back to projects

The problem

Getting a model to write an app is the easy part. One generation call returns something that looks finished, and nothing has checked it, reviewed it, or recorded how it was made.

What one-shot generation leaves out
  • No review by anything other than the model that wrote the code.
  • Fixes that rewrite parts of the app nobody asked to change.
  • No point where a person decides whether it ships.
  • No record afterwards of what was asked, found, fixed and approved.
What the pipeline has to guarantee
  • Every build passes the same automated checks before review.
  • A second model audits the output, from a different provider when one is configured.
  • Fixes are scoped by a written plan, and the resulting diff is checked against that plan.
  • Nothing merges without an explicit approval, and every run leaves a record.

The pipeline

Fourteen steps from prompt to deployed app. Each one reports its status in the chat as it runs.

Stages, in order
Steps 0–13
  • Branch — a new Git branch per build, so nothing touches main until approval.
  • Plan — the model writes a plan before any code.
  • Build — Claude writes the app, streaming a live preview.
  • Checks — 30 automated checks across syntax, accessibility, responsive layout, security, performance, PWA and structure.
  • Audit — a second model reviews the code and returns a list of issues with severity and location.
  • Fix — up to 3 passes: plan the patch, apply it, validate the diff, then re-run checks and audit.
  • Enhancement review — a reviewer proposes improvements and flags remaining bugs.
  • Implement — Claude applies the accepted enhancements.
  • Final review — a last bug gate before anything is pushed.
  • Backend — optional backend setup for apps that need one.
  • Push — the build is committed to its branch through the GitHub API.
  • Preview — the app renders live in the chat.
  • Approval gate — a person approves or asks for changes.
  • Merge — the branch merges to main and GitHub Pages deploys it.

Multi-pass review and scoped fixes

The part I spent the most time on. Letting a model “fix the issues” freely is how working features get broken, so the audit and the fix are joined by a contract.

The patch plan
Before the fix
  • After the audit, the model writes a patch plan as structured JSON: scope, sections it will touch, sections it must not touch, each change, constraints, a risk level and a line budget.
  • The plan carries a hash of the audit it answers, so a plan cannot be reused against different findings.
  • Seven deterministic checks run on the plan before any code changes: schema, audit-hash match, section consistency, no overlap between touched and protected sections, a risk gate (high-risk plans are limited to 5 changes), coverage of every high-severity finding, and a sane line budget.
  • A plan that fails is regenerated once with the failure reason.
Validating the diff
After the fix
  • After the fix, the new code is compared with the old and checked against the plan. Six checks:
  • Protected sections are unchanged.
  • The change stays inside the line budget.
  • No new external dependencies.
  • CSS variables, localStorage keys and existing functions are all still there.
  • Each pass and its result are stored on the build record. The loop stops after 3 passes.
A checkpoint for the person
  • After the first audit the pipeline pauses and shows the issues found.
  • The user decides whether to fix them or continue; the decision is recorded.
  • The patch plan is generated in parallel, so the pause costs no time.
More than one model provider
  • Claude plans, builds and fixes.
  • The reviewer is chosen by what is configured: Gemini first, then GPT, with Claude as the fallback.
  • Calls go through one module with retries, timeouts, prompt caching and per-call usage tracking.
  • Cost is totalled per build and shown with the result.

Structured outputs and audit logging

Every build produces a record that can be read later without the chat transcript.

The build record
  • Inputs: prompt, pipeline mode, template, whether images were attached.
  • Intermediate artifacts: the plan and the model’s reasoning.
  • Quality data: check results, audit findings, enhancement review.
  • Each fix pass, the checkpoint decision, the approval decision and how long approval took.
  • Outcome: final code size, final check score and cost.
Events
  • Each step emits a typed event with a build ID, timestamp, pipeline and schema version.
  • Events and the last 50 build records are kept on the device.
  • With Supabase configured, events sync to a table for analysis across builds.
  • A quality score and a satisfaction score are computed per build and feed template recommendations.
Key handling
  • A guard wraps fetch and blocks any request that carries an API key to a domain outside an approved list.
  • Keys are scrubbed from error messages before they are logged or shown.
  • An optional server-side proxy keeps provider keys off the device; its usage table is protected by row-level security so users read only their own rows.
Stack
  • App — vanilla JavaScript (ES modules), Vite, installable PWA.
  • Models — Claude, GPT, Gemini.
  • Delivery — GitHub API for branches, commits and merges; GitHub Pages for hosting.
  • Backend — Supabase for sign-in, usage and event sync.

What this does not claim

The same rule as the rest of the portfolio: say what the thing is, and what it is not.

Limits
  • The automated checks are static checks on the generated code. They are not a test suite and do not prove the app behaves correctly.
  • A second model’s review reduces defects; it does not remove the need for the approval gate.
  • Generated apps are single-file web apps. This is not a general-purpose software factory.
  • Build records live on the device unless sync is turned on.
